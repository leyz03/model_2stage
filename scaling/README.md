# 规模实验：n、T、场景数 K_s 对求解性能的影响

状态：**已完成（2026-10-04）**。算法见 [../04_algorithm.md](../04_algorithm.md)。

## 怎么跑

在 `/global/home/users/zjl0512/sddip` 下：

```bash
python3 model_2stage/scaling/build_scaling_instances.py                      # 实例（约 30 s）
sbatch --time=12:00:00 --export=ALL,RUNS="oracle:8:4:3+oracle:5:6:3:pre/lazy",OPTS="--mip_tl 300" \
       model_2stage/scaling/slurm_scaling.sh                                  # 单场景 MILP 成本
sbatch --time=24:00:00 --export=ALL,RUNS="bnb:5:4:50:pre+ef:5:4:50",OPTS="--tl 1800 --mip_tl 300" \
       model_2stage/scaling/slurm_scaling.sh                                  # 两阶段求解
sbatch --export=ALL,ARGS="--n 3 --T 4+6+8 --nscen 2 --milp --phi 0" model_2stage/scaling/slurm_diag.sh   # LP 诊断（HiGHS）
python3 model_2stage/scaling/summarize.py <job ids>                          # 汇总表
```

RUNS 的每项是 `mode:n:T:nscen[:inner]`，项之间用 `+`，多个 inner 用 `/`。**不要在 RUNS / ARGS 里用逗号**：`sbatch --export` 会在逗号处截断。

**剪枝（2026-10-04 起默认开启）**：每项运行开始前由 `prune.py` 检查。若同一 mode（bnb 还要求同一 inner）在 $n'\le n$、$T'\le T$、$K_s'\le K_s$
的某个配置上已经失败，这一项就跳过。失败的定义：
- bnb：撞时限或没有可行解；
- EF：状态不是 OPTIMAL；
- oracle：有 MILP 撞了时限。

检查范围是本作业的记录，以及 `PRUNE_JOBS="jobid ..."` 列出的历史作业；`PRUNE=0` 关闭剪枝。RUNS 要按从小到大排列，规则才能起作用。
分支定界在运行内部也会按截止时间停止：每个场景 MILP 前检查时间，单个 MILP 的时限不超过剩余时间。超时后，当前节点放回队列并保留它的上界。

## 实例族

每个节点的密度固定，只改变规模：
- 节点均匀落在单位正方形里；骑行时间 $c\in\{1,2,3\}$，工人路程 $d\in\{1,2\}$（同节点为 0）；
- 每个节点 4 辆车、2 名工人；
- 平均每节点每期 1.4 次出行，早晚两个高峰，方向相反；
- 经济参数同 toy：$R=10$、$C_p=5$、$\phi=0.15$，3 档电量，Γ=10；
- 价格菜单为 0 到（最大门槛 + 4）。

场景池：train 200 条、eval 500 条，抽样规则同 toy。

## 结论

1. **分支定界的总时间 ≈ 价格点数 × $K_s$ × 单场景 MILP 时间 $t(n,T)$ + 松弛部分。**
   - 价格点数基本固定在 10 到 15 个，因为价格结构只有两组，且有菜单约简。
   - $K_s$ 只是线性因子。
   - 决定能不能解的是 $t(n,T)$。
2. **$T$ 的影响最猛**：$n=3$ 时，$T$ 从 4 到 12，单场景时间约增长 3000 倍；分支定界的总时间每多一期乘以 2 到 3。根源是小数车造成的 LP 差距（第 2 节），这是建模层面的问题，不是算法问题。
3. **$n$ 次之**：$T=4$ 时，$n$ 从 3 到 20，单场景时间约增长 $10^4$ 倍，大约按 $n^5$ 走；而二元变量数按 $n^3$ 增长。分支定界在 $n\le8$ 能证明最优，$n=12$ 已经不行。
4. **场景数最温和**：分支定界线性增长，EF 超线性增长。$K_s\ge25$ 时分支定界开始领先，$K_s=50$ 时快 12 倍。EF 在 $n\ge8$ 或 $T\ge6$ 时 30 分钟都关不掉 gap，还常常找不到可行解。
5. **内层写法**：
   - pre 写法稳定地比 full 快（$n=12$ 时快 3.5 倍）；
   - lazy 割只在大 $n$ 时划算（$n=20$ 时比 pre 快 2.5 倍），小规模时慢 5 到 35 倍；
   - lazy 在 $T=8$ 时会出现撞时限而没有可行解的情况，因为 lazy 约束会拒绝启发式找到的不稳定解。
6. **松弛几乎免费，而且很紧**：$T=4$ 时松弛比精确快 100 到 400 倍，差距在 1% 以内。$T=8$ 时只快 3 倍左右，因为难点在物理部分，而松弛也包含物理部分。

## 下一步建议（按预期收益排序）

1. **在价格点上先用松弛求值**：先解松弛（无稳定匹配），再用多项式时间检查它的解是否稳定。如果稳定，它就是精确最优，可以省掉精确 MILP。$T=4$ 时多数场景松弛值等于精确值，预期能把精确求值的成本降低一到两个数量级。
2. **把掉档改成整数**（EXP-BATTLVL §7.3 的建议）：诊断显示 Γ=1 时，$T=12$ 的 LP 差距约 1%、单场景约 1 s。这会改变模型，需要你决定。
   **2026-11-01：**已经改成整数（TODO #1，[../int_flow/README.md](../int_flow/README.md)）。n = 30、T = 100、价格 4 下整天 LP = 精确最优值（weekly/2026-10-31_11-06/TODO.md"#2 实验结果"）。
3. **按场景并行**：各场景 MILP 互相独立，但 Gurobi WLS 只有 2 个会话；HiGHS 没有会话限制，可以并行，但单个更慢。
4. **lazy 改为按规模切换**：$n\ge12$ 时用 lazy，并给 Gurobi 一个由 pre 写法得到的初始可行解，避免 $T=8$ 时出现"没有可行解"的情况。
